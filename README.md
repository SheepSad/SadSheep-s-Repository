# 一、通用素养

## 1.Git操作：  

- 分支是从某个提交点分出的独立开发线路，在不影响主线的情况下并行修改；合并是把一条分支上的改动整合回另一条分支，从而把两条开发线路汇合成一条。

## 2.命令行：

### 文件与目录操作

| 命令 | 用途 |
|---|---|
| `cd <目录>` | 切换当前工作目录；`cd ..` 返回上一级，`cd ~` 回到用户主目录，`cd -` 回到上次所在目录 |
| `ls` | 列出当前目录下的文件和子目录；`ls -l` 看详细信息（权限、大小、时间），`ls -a` 显示隐藏文件 |
| `mkdir <名称>` | 新建目录；`mkdir -p a/b/c` 一次创建多级目录，父目录不存在也能建 |

### Git 常用命令(暂列较为熟练的命令)

**仓库与暂存**

| 命令 | 用途 |
|---|---|
| `git add <文件>` | 把改动加入暂存区，准备提交；`git add .` 添加全部 |
| `git commit` | 把暂存区内容提交为一条新记录 |

**分支与同步**

| 命令 | 用途 |
|---|---|
| `git branch` | 列出本地分支 |
|`git branch <名>`| 新建分支 |
| `git switch <分支>` / `git checkout <分支>` | 切换到指定分支 |
| `git merge <分支>` | 把指定分支合并进当前分支 |

## 3.MIT LICENSE ：

MIT 用“几乎不设限 + 免责 + 只要求保留声明”换取最大范围的采用，是开源项目最常用、最省心的选择。

### 对使用者

- **极其宽松**：可以自由使用、修改、分发、商用、闭源再发布，几乎没有限制。
- **易读易懂**：全文只有一段话，审核成本低。
- **兼容性好**：可与 GPL、Apache 2.0 等大多数许可证共存。

### 对作者

- **保留著作权**：你仍拥有版权，只是授权他人使用。
- **免责**：明确声明软件“按原样”提供，不承担任何担保或损害责任，降低法律风险。
- **促进采用**：门槛最低，最容易被人拿去用、被项目引用、被公司采纳，有利于传播和积累声誉。
- **署名要求轻**：只需在使用/分发时保留版权声明和许可证原文，不必公开衍生代码。

### 代价与注意点

- **无专利授权条款**：无明确授予专利许可，对使用者保护较弱。
- **不要求回馈**：他人可以拿你的代码做闭源商业产品而不回馈社区。
- **不提供商标授权**：不能使用作者的名义或商标做推广。

# 二、小游戏(2048)+自动AI求解

>零第三方依赖，只使用 Node 内置模块与系统已安装的 Edge/Chrome（通过 DevTools 协议驱动）：

| 文件 | 说明 |
| --- | --- |
| `2048.html` | 2048 游戏本体（拥有深色/浅色主题，合成动画、实时计分、历史战绩记录等） |
| `play2048-ai.mjs` | 用 expectimax AI 自动操作这个游戏，输了自动重开，直到赢下 2048 |

## 1.快速开始命令

```bash
node play2048-ai.mjs              # 打开 2048.html，AI 自动玩到 2048 获胜（无头浏览器）
node play2048-ai.mjs --head       # 想亲眼看它玩就加这个，会弹出浏览器窗口
node play2048-ai.mjs --head --every 75   # 实时围观，同时每 75 秒抓一张过程图到 ai-shots/
node play2048-ai.mjs --fast       # 加速模式，压缩动画等待
node play2048-ai.mjs --sim        # 不开浏览器，直接执行页面脚本（CI / 沙箱环境可用）
node play2048-ai.mjs --bench 20   # 纯自我对弈 20 局，输出胜率与平均得分
node play2048-ai.mjs --selftest   # 校验 AI 的走子规则与游戏内实现完全一致
node play2048-ai.mjs --help       # 全部参数
```

只想玩的话，直接双击 `2048.html` 即可，不需要 Node。

## 2.AI求解逻辑

1. **启动浏览器**：自动探测 Edge / Chrome，用CDP `--remote-debugging-port` 打开游戏页；
   启动方式会按「现代无头 → 旧版无头+单进程 → 无头+单进程 → 关闭沙箱」依次重试，
   以适配禁止创建命名管道、导致 Chromium 多进程 IPC 崩溃的受限环境。
2. **读棋盘**：从 DOM 里读每个 `.tile` 的 `--x` / `--y` 与文本值，还原成 4×4 棋盘。
3. **思考**：  
- expectimax 搜索  
玩家节点取最大期望，机会节点枚举“在哪个空格生成 2 还是 4” 并按 0.9 / 0.1 概率加权。棋盘用指数编码（0=空，11=2048），行合并结果用 65536 项的查找表预计算，选出最优方向，搜索全程零内存分配。
- 启发式评估函数  
通过几个经典维度评估：  

|函数|名称|目的|
|---|---|---|
|empty|空格数|留出腾挪空间，是最重要的生存指标|
|mono|单调性|行列数值尽量单向递增/递减，便于把大数挤到一角|
|smooth|平滑度|相邻数值差越小越好，便于将来合并|
|merges|可合并对数|相邻同值对数，直接奖励“马上能合”的局面|
|maxE|最大方块指数|鼓励养大数字|
|corner|最大块贴角额外奖励|保证游戏能够长时间进行|

4. **操作**：用CDP `Input.dispatchKeyEvent` 发送真实方向键事件，和真人按键走的是同一套逻辑。
5. **直到胜利**：出现 2048 就结束并截图；若这局走死就自动重开，默认最多尝试 20 局，可修改。

## 3.棋力调节方式

```bash
node play2048-ai.mjs --depth 4              # 搜得更深，更强也更慢
AI_W_MERGES=0 AI_ADAPTIVE=0 node play2048-ai.mjs --bench 10   # 消融实验
```

## 4.本机实测结果

在本机（Edge，实时模式）环境下运行默认配置：

| 场次 | 结果 | 步数 | 得分 |
| --- | --- | --- | --- |
| 无头浏览器 | 第 1 局获胜 | 953 | 20196 |
| 弹窗演示 `--head` | 第 1 局失败（最大 1024）→ 第 2 局获胜 | 955 / 1015 | 16148 / 20516 |
| `--sim` 无浏览器 | 第 1 局获胜 | 967 | 20304 |

- 单局胜率不是 100%（这是 expectimax 的固有方差），所以程序内置了失败重开。
- 只要单局胜率大于 0，连续 N 局都失败的概率会指数衰减，默认 20 局足够稳。

## 5.注意事项

- `--sim` 模式不重新实现游戏，而是把 `2048.html` 里那段 `<script>` 原样取出、
  装进一个最小 DOM 里执行，再通过它自己的 `keydown` 监听器“按键”。
  跑的就是页面里那份真实逻辑，只是没有渲染。
- 游戏里的 `isGameOver()` 原本会在棋盘没满时抛异常（`g[y][x+1]` 可能是 `null`）。
  浏览器里这个异常被定时器回调吞掉了所以不易察觉，但确实每次移动都在报错。
  已修复为「先判空再取值」。


# 三、Croc论文学习笔记

> **论文思路**：通过搭建Croc平台，用全开源的芯片设计链条替换传统教学里"商业 EDA 许可证 + NDA 保密 PDK + 闭源 IP"的高门槛，从而让大量学生能够真正经历从 RTL 到流片的完整芯片设计流程。

---

## 1.总体流程

```
                 		  ┌─────────  前端（验证设计正确性） ──────────┐
sw/filename.c ──riscv gcc──► filename.hex ──► Verilator 编译整个 SoC RTL ──► 仿真：JTAG 装载、核执行、UART 打印
                 		  └───────────────────────────────┘
                 ┌──────────────────  后端（从设计到芯片） ────────────┐
 RTL(SV) ──Bender 文件清单──► Yosys(slang 前端)综合 ──► 门级网表 ──► OpenROAD 布局布线 ──► GDS ──► KLayout
                 └─────────────────────────────────────────┘
```

## 2.前端Verilator仿真

**第一步：编译测试程序**
- 用RISC-V把 `helloworld.c`程序等变成 `helloworld.elf`再用 objcopy 转成 Verilog 十六进制格式 `helloworld.hex`，供仿真器载入 SRAM。

**第二步：Verilator 编译整个 SoC**

1. **Bender 生成文件清单** ：把 SoC 全部 SystemVerilog 源文件按依赖顺序列出来。
2. **Verilator 编译**：把SystemVerilog 转换成 C++，再用 g++ 编译成可执行的模型。

**第三步：运行仿真**

- JTAG(Corc目前只有JTAG一种启动方式)把程序装进 SRAM、唤醒核后检查UART 输出是否符合预期。

## 3.后端运行

1. **准备**：选定 PDK，建立符号链接；Bender 生成 ASIC 文件清单。
2. **SystemVerilog 解析**
3. **工艺映射**
4. **输出**：交给 OpenROAD 的最终网表、带层级注释的调试网表与`reports/` 系列报告。

## 4.项目运行数据证明（由AI收集）

### 前端Verilator仿真  

仿真器里的 testbench扮演 JTAG 调试主机，完整模拟了真实芯片的 bring-up 流程：

| 时刻 | 事件 |
|------|------|
| 42.1 µs | JTAG/DMI 初始化成功 |
| 42.1 µs | 经 JTAG 向 SRAM 地址 `0x1000_0000` 写入 `0x1234_5678` 再读回校验（内存自检） |
| 94.65 µs | 读回数据正确 |
| 94.65 µs | 经 JTAG 把 `helloworld.hex` 逐字写入 SRAM `0x1000_0000` |
| 1.41 ms | 写 CLINT 寄存器（`0x0204_0000` 的 msip 位）唤醒核心 |
| 1.45 ms | 核心解除 halt、开始执行 |
| **3.47 ms** | **UART 输出 `Hello World from Croc!`**（逐字节 0x48 0x65 … 0x0a） |
| 3.50 ms | `[JTAG] Simulation finished: SUCCESS`，`$finish` |

仿真报告：4 ms 仿真时间 / 2.38 秒墙钟时间（约 1.25 ms/s 仿真吞吐）。

### 后端运行：

| 指标 | 数值 |
|------|------|
| 单元总数 | **27,439**（含 2 个 SRAM 宏 RM_IHPSG13_1P_512x32、64 个 IO 焊盘单元） |
| 触发器 | 4,153 个 `sg13g2_dfrbpq_1` |
| 芯片单元面积 | **1.535 mm²**（Liberty 面积和；时序单元占 13.25%） |
| 结构检查 | `check`：0 problems |
| 顶层 | `croc_chip`，52 个端口（含 32 个 GPIO 焊盘、VDD/VSS/VDDIO/VSSIO） |

综合前的 elaborated 统计：13,190 个 RTL 级单元、164,771 根线网——综合把 RTL 级操作（$add/$mux/...）全部落成了具体门电路。

### 综合后网表仿真（前端 × 后端闭环）

用 **同一份** `helloworld.hex` 去仿真**综合后的门级网表**（UDP 原语表）：

```
@ 3.473 ms | [UART] Hello World from Croc!   （与 RTL 仿真逐字节一致）
@ 3.500 ms | [JTAG] Simulation finished: SUCCESS
```

RTL 仿真（3.473350 ms）与网表仿真（3.473300 ms）输出时间几乎一致——**证明 Yosys 综合没有改变设计功能**
